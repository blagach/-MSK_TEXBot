# Одна проверка в Shell без доступа к аккаунту

Проверяемый кандидат приложения: `a5f4eb98877c56fe384b55ff212081af485dee2c`.
Точный кандидат отката: `cec41d17431c458aafb54242397116c419246848`.
Установленный Worker должен оставаться на `31d2e0170451fb85ebd7c986ff777cb675881104`.

## Действия владельца

1. Использовать новую закреплённую команду из отчёта об исправлении. Исторический
   `snapshot_sha256` уже передан владельцем:
   `92555b1828b18f6e082fe33ef3e1774efb648b617926d05ab3413f01e59d2f7f`.
   Он передаётся в main(checksum) явно; ввод через терминал не требуется.
2. Открыть Shell только `msk-texbot-test`, ID `srv-dboqc51srm7s73cppi00`.
3. Вставить закреплённый блок загрузки из отчёта Work №1. В нём проверяются ID Worker,
   установленный SHA и SHA-256 самого загрузчика перед исполнением. Никаких правок
   установленного каталога приложения или deploy для получения инструмента не требуется.
4. Команда не запрашивает ввод: дождаться завершения пяти проходов на новой копии.
5. Дождаться JSON. При `STOP` ничего не исправлять в базе и не удалять; передать результат.
   При `ok` передать JSON целиком: в нём только ревизии, пути, хеши и количества.

Если обычный Shell не предоставляет Git, нужный Python или доступ к публичному
GitHub, команда остановится. Пакеты, Git и сертификаты автоматически не устанавливаются,
запросов паролей и обходов ограничений нет. Для ручного запуска через свой Shell
авторизация в браузере агента вообще не требуется.

## Исправление ошибки терминала

Предыдущая попытка владельца вернула `File or stream is not seekable.`. Точное
воспроизведение на локальном псевдотерминале: `open(path_to_tty, 'r+')` выбрасывает
`io.UnsupportedOperation` с тем же текстом, ещё до чтения хеша. Двунаправленное
текстовое открытие требует seekable-поток. SQLite, hashlib и tarfile в этом месте
ещё не вызываются. Вспомогательные модули работают с обычными файлами и BytesIO,
не с терминалом. Исправление удаляет зависимость от `/dev/tty` и stdin полностью.

Для этой ошибки в указанной версии вызов run() ещё не наступил, поэтому каталог
репетиции не должен был создаться именно этой попыткой. Это вывод по коду, не
осмотр Render. Любые уже существующие файлы и каталоги всё равно сохраняются.
Повторный запуск использует новый mkdtemp-каталог и не возобновляет старый.

Регрессионный тест воспроизводит ошибку старого открытия реального PTY, затем
проверяет новый main(checksum) с запрещённым обращением к терминальному вводу.
Отдельно проверены отказ без явного хеша и сохранение каталога предыдущей попытки
при полном прогоне на локальной SQLite. Неуспешная попытка владельца не считается
завершённой проверкой фактической миграции и отката.

## Что делает загрузчик

`render_snapshot_check.py` сверяет ровно два ранее названных файла в `/var/data/backups`:
`test-20261111T165141677395Z.sqlite` и `restore-candidate-20261111T165141687887Z.sqlite`.
Их хеши должны совпадать с введённым историческим SHA-256. Проверяет приватность каталога,
модули и запас свободного места. До этого новые файлы не создаются.

Далее создаётся новый приватный каталог `owner-rehearsal-*`. В нём размещается отдельный
полный clone публичного репозитория без checkout и без использования сохранённых Git
учётных данных. Из точного коммита инструмента `22518ef78905157c14ce44a71fce659b3e0236bb`
берутся только два вспомогательных Python-модуля. Публичный GitHub получает запрос к коду,
а не снимок SQLite или данные пользователей. Зависимости не устанавливаются.

Пять проходов: кандидат → кандидат → откат → откат → кандидат. Инициализация схемы
происходит только в новой `working.sqlite`. Сохраняется ещё одна новая мигрированная
база для сравнения строк после отката. Проверяются все исходные таблицы и все строки,
а не только заявочные счётчики: заявки, отклики, пользователи, исполнители, черновики,
журнал и прочие таблицы. SQLite integrity_check и foreign_key_check проходят после
каждого шага; исходный снимок и прежний восстановленный файл повторно хешируются.

Дополнительно каждый код должен распознавать все сохранённые состояния черновиков,
читать JSON черновиков как объекты и соблюдать записанные роли и ограничения доступа.
Нераспознанное состояние или политика останавливают проверку. Пустые таблицы не
считаются ручной функциональной приёмкой.

Дочерние процессы приложения не получают действующих секретов. dotenv отключён,
на уровне Python audit запрещены сетевые подключения, запуск программ и SQLite
вне новой рабочей копии. start(), polling и startup диспетчера не вызываются;
очереди уведомлений не восстанавливаются. Файлы сохраняются при успехе и ошибке.

## Готовность и восстановление

Сейчас бэкап подтверждён владельцем (27 таблиц), но результат фактической репетиции
миграции/отката ещё не получен. Тестовое обновление не разрешено.

После JSON `ok` сверить все пять проходов, 27 исходных таблиц и неизменность существующих
копий. Это проверка хранения, состояний черновиков и политик; прохождение пользовательских
сценариев C05/E01 остаётся ручным. Для релиза повторно сверить точные SHA/CI, тестовый
Worker/диск и autoDeploy off. Поскольку установленная ветка `test/render-waste-pr9`
отличается от ветки разработки, не использовать Deploy latest без отдельного
согласованного плана переключения только тестового Worker.

Риски: незнакомые старые состояния, нехватка места, несовместимость схемы или библиотек,
отличия поведения UI. Откат cec41d1 не содержит добавленного в a5f4eb9 аудита
прерванной доставки поддержки. Он должен сохранять уже записанные события и новые данные.

План восстановления при будущем разрешённом обновлении: остановиться на первой ошибке,
сохранить журналы и текущую БД; оценить точный испытанный откат кода cec41d1 на текущей
схеме с учётом новых записей. Кодовый откат требует разрешения. Восстановление старого
снимка поверх действующей базы — отдельная операция с риском потери новых записей,
требует отдельного письменного разрешения и сверки различий. Автоматического восстановления
или удаления нет. Рабочий @MSK_TEXBot не затрагивается, C05/E01 открыты,
финансы и рассылки не активируются.
