## Перед запросом разрешения и запуском

1. Войти в Shell именно тестового Worker; подтвердить ID srv-dboqc51srm7s73cppi00, диск /var/data и путь test_database_path(). Не выводить токены.
2. Зафиксировать свежий точный SHA кандидата и успешный Actions. Не нажимать Deploy latest для прежней ветки.
3. Приостановить ручное тестирование. Выполнить `python render_test_backup.py snapshot` в тестовом Shell. Независимо сверить SHA-256 созданного файла. Действующий SQLite-файл не копировать обычным cp при активной записи.
4. Выполнить `python render_test_backup.py restore-candidate --backup <точный_путь> --sha256 <точный_хеш>`. Команда создаёт новый файл и отказывается перезаписывать существующий. Сверить все таблицы/строки через verify_preserved_rows, целостность и внешние ключи. Проверить №8/9/11/14 и все существующие отклики, пользователей, технику, обращения и черновики, если такие ID имеются в фактической базе.
5. На ещё одной отдельной копии запустить инициализацию схемы точного кандидата дважды, без polling/Telegram-отправок. До и после сравнить исходные строки. Не указывать действующую базу как путь проверки.
6. Подготовить и испытать точный совместимый коммит отката. Он обязан понимать LeadForm.attachments, предпочтения исполнителя, независимые отклики, FindUser, ManageAdmins и ManageAccess и сохранять проверки user_access_events. Откат интерфейса не должен возвращать отозванные права или отключать ограничения. Если это не подтверждено на копии — deploy запрещён.
7. Отдельно запросить разрешение владельца на точный тестовый SHA с результатами фактического бэкапа и отката.
8. Только после разрешения выполнить один ручной deploy на тестовом Worker; autoDeploy оставить off. Проверить Live/SHA/путь SQLite, журналы и сохранность данных. При ошибке остановиться. Восстановление копии поверх действующей базы требует отдельного согласия и учёта новых записей.

## Точные действия владельца для проверки копии без обновления

Эти команды выполнять только в Shell **msk-texbot-test**. Не открывать Shell рабочего сервиса. Они не запускают polling, не делают deploy и не мигрируют действующую базу. Сейчас их выполнение на фактическом Worker не подтверждено.

1. Проверить сервис и путь без вывода токенов:

```bash
python -c 'import os; from render_test_start import TEST_WORKER_ID,test_database_path; assert os.environ.get("RENDER_SERVICE_ID")==TEST_WORKER_ID,"Wrong Worker"; print("Test Worker:", TEST_WORKER_ID); print("Test SQLite:",test_database_path())'
```

При несовпадении/ошибке остановиться. Ожидается тестовый Worker `srv-dboqc51srm7s73cppi00` и его `/var/data/bot.db` на отдельном диске.

2. Создать новый снимок стандартным SQLite backup API:

```bash
python render_test_backup.py snapshot
```

Сохранить точный путь `/var/data/backups/...sqlite` и SHA-256 из вывода. Если проверки не прошли, не удалять получившийся файл и не продолжать.

3. Независимо проверить хеш. Вместо `ПУТЬ_КОПИИ` подставить точный путь из шага 2:

```bash
python -c 'import hashlib,sys; from pathlib import Path; p=Path(sys.argv[1]); print(hashlib.file_digest(p.open("rb"),"sha256").hexdigest())' 'ПУТЬ_КОПИИ'
```

Хеш должен полностью совпасть. При несовпадении остановиться, ничего не восстанавливать поверх действующей базы.

4. Восстановить исключительно в новый файл. Подставить точный путь и хеш:

```bash
python render_test_backup.py restore-candidate --backup 'ПУТЬ_КОПИИ' --sha256 'SHA256_ИЗ_ШАГА_2'
```

Команда сама проверяет контрольную сумму, целостность, внешние ключи и совпадение исходных строк. Вывод должен содержать новый путь `restore-candidate-...sqlite`. Это не замена `/var/data/bot.db`.

Для отчёта нужны только: ID тестового Worker, пути двух файлов, совпавший SHA-256, число проверенных таблиц, количества записей и результат наличия контрольных ID. Токены, телефоны и тексты переписки не присылать.
