## Клавиатуры — B01/B05, итоговая приёмка G05/G08

Причина: `admin_ui.admin_action` и ветви справки отправляют новые сообщения,
но не имеют общей актуальности предыдущих кнопок. Проверка ID панели есть
у заявки/каталога/части регистрации, но она не охватывает всю навигацию.

Воспроизведено через настоящий Dispatcher с подставным Telegram transport:
`/support` → `/menu` → запоздалый `help:new:bug` из старого сообщения.
Без защиты возникает `Support:compose`. С исправлением обработчик не вызывается,
состояние остаётся пустым. Это подтверждение причины, а не живая приёмка Telegram.

Общий механизм `screen_controls.py`:

- Хранит текущие панели отдельно от черновиков в существующем FSM, без новой схемы.
- Инвалидирует старые действия до отправки нового экрана, затем убирает их кнопки
  через `editMessageReplyMarkup`. История сообщений не удаляется.
- Блокирует запоздалые callbacks даже при отказе Telegram изменить сообщение,
  перезапуске или неопределённом результате новой отправки. Повторов отправки нет.
- Сохраняет все карточки одного экрана техники до ухода с него. Ошибка ввода
  оставляет текущие кнопки; следующий текстовый шаг закрывает предыдущие.
- Сохраняет исторические ссылки на заявки, контакты, обращения и команды модерации;
  их существующие проверки владельца/прав/статуса продолжают действовать.
- Не вмешивается в фоновые задачи и уведомления другим адресатам.
- Учитывает ReplyKeyboard/ReplyKeyboardRemove; существующая обычная клавиатура
  уже имеет `is_persistent=True`. Проверки текстовых команд по FSM сохраняются.

Ограничения: Bot API не позволяет прочитать всю старую переписку. ID старых панелей,
не сохранённые до установки исправления, нельзя заранее найти все. После нового
экрана старые временные callbacks блокируются по границе сообщений; при нажатии
также предпринимается визуальная очистка. При отказе редактирования кнопки могут
оставаться видимыми, но действие блокируется. Живая приёмка тестового бота впереди.

## Оплата — согласованный объём ТЗ-7, подкритерии G05/G08/G09

| Контур | Реализовано | Отсутствует |
|---|---|---|
| Расчёты за работу техники | Формы расчёта в профиле и заявке, `payment_preferences.py` | Это не приём оплаты сервиса; A16 не отменяется |
| Доступ к контакту | Бесплатный доступ, сохранение повторного открытия | Платные права, лимиты, срок, исключения, сохранение купленных прав |
| Тарифы | Утверждены типы; цены/лимиты не утверждены | Версии разового контакта, пакетов, подписок, пробных/индивидуальных условий, промокодов |
| Заказы и подтверждение | Нет; `PAYMENT_URL` не является платёжным контуром | Заказ, сумма/валюта/версия, состояния, песочница, серверная аутентификация, идемпотентность, защита двойной выдачи |
| Приём денег | Нет провайдера и серверного обработчика | СБП/карта, «💳 Оплатить сейчас», чек; не выдавать права по скриншоту/возврату браузера |
| Учёт и финансы | Роль finance; экран — заглушка | История, комиссии/возвраты/чистый результат, права, аудит, фискальные данные |
| Режим/продление | Только бесплатный режим | Подтверждение владельца, расписание МСК, пауза списаний, ручное продление с остатком, напоминания, предупреждение о тарифах за 7 дней |

Согласован защищённый переход СБП/карта с серверным подтверждением; Telegram
invoice/Stars как обязательная архитектура не утверждены. Для настоящей интеграции
нужны решения о провайдере, тарифах/лимитах, пробном доступе, договоре/чеках.
Это не мешает локальному ядру с подставным провайдером и явно тестовыми параметрами.
Подключение и реальные списания запрещены.

## Учёт и следующие этапы

Сохраняются 67 ID и итог 58/6/3. B05 остаётся «требует проверки»; локальное
исправление не заменяет установку/приёмку. A18/A20/E01 остаются открытыми.

реализацией финансов и рассылок.

1. Кандидат клавиатур: автоматическая проверка, отдельная ветка и CI. До разрешения

   принятого каталога/B04 и без создания заявок/техники.
2. Локальное ядро заказов/прав/идемпотентности с подставным провайдером, бесплатным
   режимом по умолчанию и проверками повторного подтверждения.
3. Локальные черновики/сегменты/согласия/предпросмотр/подтверждение кампаний, затем
   исполнение с подставным транспортом и отчётом. A18/A20 проверять отдельно.

Production/test SQLite, Worker, Render, резервные копии и PDF не меняются.
Новые пользователи и реальные платежи/массовые отправки запрещены.

включая 9 новых регрессий. Изолированная SQLite сохраняет исходные строки и схему;
`integrity_check=ok`, нарушений внешних ключей нет. Отдельно воспроизведён дефект
при отключении общей защиты. Эти проверки не являются Deploy или живой приёмкой.
