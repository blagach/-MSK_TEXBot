# Ручная приёмка C05 и E01 — минимальные действия владельца

Только тестовый бот @Msktex_test_dmitry_bot на a5f4eb98877c56fe384b55ff212081af485dee2c.
Новых deploy, откатов, удалений, изменений рабочего бота или тестовых прав не требуется.
Этот сценарий подготовлен; живые записи агентом не создавались, сообщения не отправлялись.

## Разделение работы

Агент проверяет GitHub/CI, установленный SHA, autoDeploy, диск, runtime-журналы и backend-события.
Владелец использует три тестовых Telegram-аккаунта: **A — обычный заказчик**,
**B — владелец/администратор**, **C — независимый обычный пользователь**.
Фактическое сопоставление ID передаётся владельцу приватно; личные ID здесь не публикуются.
В настройках тестового сервиса сохранены A/B/C с согласия владельца. Однако один штатный
Restart service сохранил прежнее окружение: в работающем процессе пока допущены только A/B.
Это подтверждено независимо чтением окружения процесса после перезапуска. Этап C заблокирован
до отдельного подтверждения применения существующей сборки с новым окружением через
Save and deploy. Новый коммит не требуется; повторное действие автоматически не запускалось.
Этапы A/B можно выполнять отдельно. Получение сообщения человеком и интерфейс нельзя подтвердить одной
строкой sent в SQLite. Если аккаунт не допущен к тесту — остановиться, список доступа не менять.

Нужны одна новая тестовая заявка и одно новое обращение. Старые записи для закрытия не использовать.
Данные сохраняются после теста, ничего не удаляется. Контакты и Telegram ID в отчёт не отправлять.

## C05: закрытие заявки с причиной

1. На **A**: /menu → роль заказчика → «Оставить заявку». В описании указать `C05 a5f4eb9 test`.
   Заполнить обычную тестовую анкету и отправить на модерацию.
2. На **B**: /menu → админ-панель → «Заявки» → «Новые», найти именно эту заявку и опубликовать
   только в разрешённом тестовом контуре. Записать её номер **N**.
3. На **B** открыть активную заявку N → «Закрыть заявку», ввести `C05 a5f4eb9 draft`.
   На предпросмотре нажать «Отмена». Заявка должна остаться активной.
4. Начать закрытие N снова с той же черновой причиной, нажать «Изменить причину» и ввести
   ровно `C05 a5f4eb9 final`. На предпросмотре должна быть новая причина.
5. Вызвать /menu и продолжить незавершённое закрытие предложенной кнопкой. Номер N и причина
   `C05 a5f4eb9 final` должны восстановиться. Нажать «Подтвердить закрытие» один раз.
   Старый предпросмотр не должен позволять повторное закрытие.
6. На **A** проверить уведомление о закрытии N и причину. Открыть заявку через «Мои заявки»:
   статус закрыт, причина та же, история сохранена.

Здесь B закрывает заявку A намеренно: так проверяется также уведомление заказчику.
Сохранение события закрытия агент сверит автоматически. Отмена, изменение и восстановление
предпросмотра требуют наблюдения владельца. Уведомление закрытия в текущем коде не имеет
отдельной надёжной записи о доставке в SQLite: нужны фактическое получение и журналы.

## E01: ответ поддержки и история

1. На **A**: /support → «Написать в поддержку», отправить ровно `E01 a5f4eb9 test`.
   Записать номер нового обращения **T**.
2. На **B**: админ-панель → «Поддержка» → новые обращения, открыть T → «Ответить».
   Отправить ровно `E01 a5f4eb9 ok` один раз. Дождаться результата отправки.
3. На **A** проверить отдельное уведомление с этим ответом, нажать «Открыть обращение».
   Тот же ответ должен быть в истории. Выйти в /menu, затем /support → «Мои обращения» → T:
   ответ должен сохраниться. Отдельного второго уведомления от открытия истории быть не должно.

При тайм-ауте, отказе или неоднозначном результате не отправлять тот же ответ повторно.
Сообщить номер T и наблюдение: агент сверит saved/sent/failed/uncertain, очередь и журнал.
Историческую причину проблемы старого обращения №2 новый успешный тест не устанавливает.

## C: проверка разграничения доступа третьим аккаунтом

Выполнять только после отдельного разрешения на применение TESTER_IDS и подтверждения агентом,
что C допущен работающим Worker. Не назначать C административную роль ради проверки.

1. На **C** открыть только тестового бота, вызвать /menu. Админ-панель не должна быть доступна.
2. Открыть «Мои заявки» и убедиться, что заявка N аккаунта A там не появилась.
3. Открыть /support → «Мои обращения»: обращение T аккаунта A не должно быть доступно.
   Не отправлять новый запрос или ответ ради этого шага.
4. На **A** повторно открыть свою заявку N и обращение T: собственная история доступна.

Это проверяет списки и видимость в интерфейсе. Защиту прямых callback-запросов агент проверяет
локальными тестами; наблюдение пустого списка само по себе такой защитой не считается.
Не удалять тестовые записи, не менять роли, ограничения, подписки или настройки уведомлений.

## Что передать агенту

Скопировать и заполнить короткий итог (без скриншотов контактов и без паролей):

```text
Заявка N=...
Обращение T=...
C05: отмена оставила заявку активной — да/нет
C05: изменение причины и продолжение через /menu — да/нет
C05: уведомление A и закрытая карточка с final-причиной — да/нет
E01: отдельное уведомление A ровно один раз — да/нет
E01: ответ по кнопке и после повторного открытия истории — да/нет
C: нет админ-панели и чужих N/T в личных списках — да/нет/пока не допущен
Замечания: ...
```

## Автоматическая сверка после действий владельца

Подготовлен `acceptance_check.py`, он использует только sqlite3 mode=ro/query_only и
согласованный read-снимок транзакции. Схему/данные не меняет, бот не импортирует, Telegram
не вызывает, сообщения не отправляет. Вход CLI ограничен тестовым Worker и установленным SHA.
Агент запускает его отдельно из проверенного кода, не обновляя Worker ради инструмента.
В установленном a5f4eb9 этого нового файла нет — команду с именем файла там вслепую не выполнять.

По N/T он проверяет: closed и единственное событие с final-причиной, один успешный аудит
закрытия с тем же актором; один вопрос A и один маркированный ответ B; sent с положительным
Telegram message ID, без ошибки; совпадение ID в saved/sent-аудите; одинаковую пару разных
аккаунтов в обоих сценариях. Неизвестные номера, чужие записи, дубли и несовпадающие события
не дают положительного backend-результата. Тексты и ID аккаунтов в JSON не выводятся.

Даже `backend_checks: ok` оставляет C05/E01 открытыми. Итоговая приёмка возможна только
после наблюдений владельца и явного подтверждения результата. Отклонения фиксируются;
исправления разрабатываются отдельно без нового deploy до разрешения.
