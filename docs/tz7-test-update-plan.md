## Объём будущего разрешения

Разрешение должно явно охватывать только согласованный тестовый Worker, один deploy точного кандидата, остановку/запуск тестового процесса и штатную добавочную инициализацию тестовой БД. Сейчас эти действия запрещены. Отдельно указать, разрешён ли при необходимости кодовый откат к точному cec41d1. Если нет — запрашивать решение перед откатом. Восстановление старого снимка поверх действующей БД в разрешение на deploy не входит.

## Порядок после письменного разрешения

1. Приостановить ручной ввод тестовых данных на окно обновления. Повторно сверить имя и ID именно тестового Worker, установленный SHA, отсутствие текущего deploy, прежние команды и диск, один экземпляр и autoDeploy off. При отличиях остановиться. Сохранить исходный обезличенный JSON успешной репетиции и его локальный отчёт, если путь есть в полном результате.
2. Проверить свободное место и наличие тестовых настроек без вывода секретов. Согласовать ожидаемую обработку уже сохранённых сервисных ответов: startup может доставить queued-ответы только разрешённым тестерам. Sending становится uncertain без повтора, незавершённые XLSX автоматически не пересылаются. Маркетинг и финансы не активировать.
3. В Dashboard именно тестового Worker выбрать **Manual Deploy → Deploy a specific commit**, вставить полный SHA a5f4eb98877c56fe384b55ff212081af485dee2c, сверить его и выполнить один **Deploy Commit**. Смена привязанной ветки не требуется. Не использовать Deploy latest, Clear build cache или connector trigger_deploy без параметра точного коммита. Если нужная опция отсутствует или SHA не принимается — остановиться.
4. Зафиксировать deploy ID и наблюдать до конечного статуса. Из-за persistent disk будет перерыв работы. Второй poller вручную не запускать. Дополнительные миграции в build/pre-deploy не добавлять: диск там недоступен.
5. Проверенный launcher сам создаёт свежий снимок более актуальной тестовой БД и отдельное восстановление, проверяет добавочную инициализацию на копии, затем выполняет только разрешённую инициализацию действующей тестовой БД и сравнение строк. Это часть будущего запуска на свежих данных, а не повтор завершённой ручной репетиции. Существующие копии сохраняются. При ошибке остановиться, не повторять deploy вслепую.
6. После Live сверить полный SHA кандидата, прежний диск, autoDeploy off, один процесс и изоляцию тестового бота. Проверить логи миграции копии и сохранения строк, отсутствие SQLite/polling/изоляционных ошибок. Background worker проверяется по процессу, журналам и поведению бота; HTTP health checks к нему не применяются.
7. С двух тестовых аккаунтов проверить /menu, обе роли, сохранённые черновики, поддержку и права. Пройти уже сохранённые сценарии C05/E01 из [приёмки](tz5-acceptance.md). C05/E01 остаются открытыми, пока владелец отдельно не подтвердит их вручную.
8. Записать фактические SHA, deploy ID, результат и отклонения в реестр. Не включать финансы/маркетинг, не переносить изменения в рабочий бот.

## Кодовый откат

При ошибке сохранить журналы и проверить фактический Live SHA. После изменения схемы не выбирать прежний старый deploy как универсальный откат: он не испытывался с новыми состояниями.

Разрешённый точный откат выполняется как **Manual Deploy → Deploy a specific commit → cec41d17431c458aafb54242397116c419246848** на том же тестовом Worker с текущей БД. Этот коммит проверен на копии, но ещё не развёртывался: наличие готового успешного build-артефакта для быстрого Dashboard Rollback не подтверждено. Потребуется сборка, мгновенный откат не обещается.

После отката снова сверить SHA, autoDeploy off, один процесс, изоляцию, данные и права. Откат не отменяет уже отправленные сообщения. В cec41d1 отсутствует улучшение a5f4eb9 для аудита прерванной доставки; ранее записанные события должны сохраняться.

## Восстановление данных и оставшиеся риски

Диск и БД не откатываются вместе с кодом. Автоматическая замена БД старым снимком, Restore disk snapshot или удаление файлов не выполняются. При повреждении сначала сохранить текущее состояние и журналы; отдельно согласовать остановку записи, восстановление и учёт записей, появившихся после снимка. Иначе есть риск потери новых данных.

Репетиция подтверждает хранение, состояния и политики на фиксированном снимке. Она не гарантирует будущую сборку, доступность Telegram, корректность фактических настроек, startup-очередей и новых данных после снимка. Нужен запас места для новых копий; очистка без согласования запрещена. Live и CI не заменяют ручную приёмку.

Техническая предпосылка по фактическому снимку выполнена. План готов к согласованию; разрешение на deploy пока отсутствует.
