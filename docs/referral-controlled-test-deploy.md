## Подтверждённое исправление

Создание заявки сохраняется прежним кодом; активация и её бизнес-история сначала коммитятся, соединение закрывается. Только затем отдельное соединение с коротким SQLite timeout выполняет необязательный реферальный учёт. Аналогично сначала сохраняются профиль и способы оплаты исполнителя, затем отдельно записывается метрика. Ошибки изолированного учёта (в том числе SQLite RAISE(ROLLBACK)) журналируются как `Referral feature failed`; основной результат и последующее штатное подтверждение/уведомление сохраняются.

Этот обработчик ошибок охватывает только необязательную SQLite-операцию, не Telegram-вызовы и не основной код. Устаревшие бизнес-ошибки не подавляются. Ошибка настройки необязательной схемы не прерывает основной запуск и закрывает реферальные входы в этом процессе. Ошибка получения доступности реферального меню не мешает обычному приветствию. При неудачной атрибуции обычное отслеживание посетителя сохраняется отдельно.

Компромисс: статистика может недосчитаться при ошибке/перезапуске между коммитами. Не выдавать эти числа за безусловно полные. Не восстанавливать счётчики автоматически и не повторять бизнес-операцию или Telegram-отправку ради статистики. Сбой общего диска или самой основной транзакции по-прежнему может нарушить работу бота; данное исправление не обещает защиту от физической недоступности SQLite.

## Единственная установка

В Dashboard TEST открыть **Manual Deploy → Deploy a specific commit**. Вставить полный SHA из разрешения, дождаться найденной записи, сверить полный SHA ссылки и сообщение коммита, выбрать её и один раз нажать Deploy commit. Не применять Deploy latest commit, Clear cache, Restart или инструмент изменения переменных. Git-ветка, start command, переменные, диск и файлы действующих БД не меняются вручную. Сохранить новый Deploy ID; следить за ним до terminal status. Начало сборки не считать успехом. Persistent disk предполагает короткий перерыв polling.

Установщик TEST уже делает собственную проверку копии перед инициализацией. Это не заменяет явно проверенные свежие копии обеих БД. После отдельного разрешения новая схема создаётся штатным кодом при запуске, а не ручной миграцией на живой БД до Deploy.

## После установки

1. Подтвердить статус Live и полный разрешённый SHA также внутри нового Worker, один instance/процесс и успешный polling только тестового бота.
2. Прочитать обе базы и сравнить с предустановочными снимками: старые строки должны сохраниться. В основной БД ожидаются ровно две дополнительные таблицы и индекс; пустые новые таблицы не должны менять старые записи. Лабораторная схема/данные не меняются этим модулем. Штатные действия участников/записи запуска разбирать отдельно по происхождению.
3. `integrity_check=ok`, `foreign_key_check=[]`, очереди и исторические неопределённые исходы сохранены. Проверить журналы с начала установки, включая `Referral feature failed`, ошибки Telegram, рестарты и неожиданные отправки. Ничего не отправлять для контроля.
4. Режим рефералов должен остаться OFF; отсутствие кнопки при OFF ожидаемо. Старые /start, lead_ и contact_ проверять безопасно с подставным транспортом на копии установленного кода. Не обращаться к Telegram-адресатам без отдельного разрешения. Не включать функцию, административную паузу заявок не переключать.
5. При успешном результате представить отчёт и остановиться. Активация TEST-рефералов, изменение BotFather /setinline и живые клиентские проверки — самостоятельные разрешения. Стандартная кнопка share/url не требует inline-режима. Визуальная приёмка iOS/Android/Desktop остаётся отдельной, не подменяется тестом структуры клавиатуры.

## Что останется при OFF

`referral_links`, `referral_attributions`, индекс `referral_by_inviter` и внутренний индекс UNIQUE остаются в SQLite вместе со всеми накопленными строками. Сохраняются audit-события `referral_mode` в `admin_action_log`, обычные bot_visitors и UI-черновики. Старые основные таблицы/колонки не меняются. Если функция ни разу не включалась, две реферальные таблицы остаются пустыми. OFF не означает удаление схемы или данных.

## План при неудаче и возможный возврат

Никаких автоматических повторных Deploy, Restart, Rollback или замены БД. Зафиксировать Deploy ID, первый сбой, текущий фактический Live SHA, Worker, очереди и состояние обеих БД; сохранить диагностику и все новые данные. Запросить решение владельца.

Предпочтительное минимальное действие при отказе только рефералов — оставить/перевести их в OFF по отдельному разрешению и сохранить основной бот. Существующие приглашения/выданные inline-карточки невозможно отозвать; новые привязки при OFF не учитываются.

Для возврата кода безопасным проверяемым ориентиром является предыдущая принятая версия `242e23ae31a87af5c4da57e008a94518295b0337`, а не ошибочный `3003ecd…` и не исходный реферальный `2626b893…`. Если фактический предустановочный TEST SHA отличается от242e23a, остановиться и заново проверить его совместимость. Временная репетиция запуска инициализаторов242e23a на расширенной схеме с новыми бизнес/реферальными записями включена в тесты: схема и все строки сохраняются, integrity/FK проверяются.

Перед любым разрешённым возвратом: остановить запуск новых реферальных действий через OFF, проверить завершение операций/очередей, сделать свежие снимки обеих баз и восстановить отдельные копии; повторить репетицию целевого старого кода на их новых данных. После отдельного разрешения выполнить установку точного согласованного старого SHA с текущими БД. Новые таблицы/индексы и все данные оставить; down migration не нужна. Не восстанавливать старый снимок поверх live и не пытаться вычесть новые записи.

После возврата на242e23a бизнес-функции сохраняются, но реферальные ссылки r1_ и старые кнопки этого раздела старым кодом не поддерживаются; ранее записанная статистика сохраняется без дальнейшего обновления. Это должно быть принято владельцем как ограничение возврата. Репетиция совместимости БД не является разрешением на автоматический откат.
