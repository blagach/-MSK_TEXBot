# Изолированная доработка заявок и откликов

База: main, ddaa93ea4a598f538430f2f7422105e51119c2e9.
Ветка: codex/safe-leads-offers. Изменения не предназначены для запуска на рабочем боте до согласования.

## Изменения

- Атомарные переходы new → publishing → published и new → rejected.
  Повторная/конкурентная модерация не переопределяет результат.
- Публикация сохраняет chat_id/message_id в отдельной таблице.
- Явный отказ Telegram (BadRequest/Forbidden) возвращает заявку в new.
  Неопределённый сетевой результат оставляет publishing даже после перезапуска.
- Отклик сохраняется до отправки; уникальность пары заявка/исполнитель предотвращает дубли.
  delivery_status: pending до результата отправки, sent при подтверждении,
  unconfirmed при ошибке. pending после остановки также требует проверки.
- Недоступность одного администратора не прерывает уведомления остальных.
- Текстовые поля ограничены по длине, телефон принимает +7XXXXXXXXXX или 8XXXXXXXXXX.
  Фотографии/пустой ввод не продвигают анкету; /cancel отменяет заполнение.
- Изменение схемы только добавляет offers и lead_publications. Существующие таблицы,
  записи и ID не удаляются и не переписываются при инициализации.

## Проверка

Python 3.12; зависимости из requirements.txt, дополнительные тестовые пакеты не нужны.

```sh
python -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python -m unittest discover -s tests -v
```

Тесты используют временные SQLite-файлы, фиктивную конфигурацию и mock Telegram.
Реальный polling не запускается. Проверяются гонки модерации, права, повторная
инициализация, сохранение отклика при сбое, дубли, неправильный ввод и ссылки.

## Ограничения и восстановление

SQLite и Telegram не образуют общую транзакцию: гарантия exactly-once невозможна.
При timeout или остановке после отправки запись может оставаться publishing,
а сообщение уже присутствовать в канале. Автоматического сброса/повтора нет.
Диспетчер должен сверить канал по номеру заявки. Только после сверки:

- Если публикация найдена: зафиксировать её chat_id/message_id через
  storage.finish_publication(lead_id, chat_id, message_id).
- Если подтверждено отсутствие: вернуть статус через
  storage.transition(lead_id, 'publishing', 'new') и повторить модерацию.

Эти функции вызываются оператором отдельно в тестовом/обслуживаемом окружении,
с правильным DB_PATH. Команды для произвольного изменения статуса через Telegram
не добавлены. Если ошибочно сбросить publishing без сверки, возможен дубль.

Отклики pending/unconfirmed нужно сверять и передавать вручную через диспетчера;
автоматическая повторная доставка и интерфейс диспетчера — следующий этап.
Повторный отклик того же исполнителя запрещён; изменение предложения пока не реализовано.
Успешная отправка означает приём Telegram, а не прочтение заказчиком.

Состояние незавершённых анкет остаётся в MemoryStorage. Нет закрытия заказа,
подбора исполнителей, проверки даты/цены по бизнес-правилам и платёжных изменений.
Сбой уведомления о новой заявке сохраняет её в leads со статусом new; очереди
повторных уведомлений в этой итерации нет. Диспетчеру нужна сверка новых заявок.

## Перед согласованным выпуском

1. На отдельном тестовом боте/канале и копии БД проверить анкеты, публикацию,
   отклонение и отклик с двух администраторских аккаунтов.
2. На остановленной копии старой БД выполнить init_db дважды, сверить существующие
   записи и новые таблицы; проверить резервное копирование и восстановление.
3. Согласовать запрет повторных откликов, формат телефона и ручной разбор ошибок доставки.
4. До запуска на рабочем окружении отдельно согласовать выпуск, остановить старый
   процесс и сделать резервную копию БД. Два polling-процесса с одним токеном не запускать.

Откат: остановить новую версию. Перед возвратом старого кода разобрать все publishing:
старый код не знает этого статуса. Новые таблицы можно оставить; старый код их не читает,
но новые отклики больше не будут сохраняться. Для полного возврата состояния используют
согласованную резервную копию, учитывая потерю записей, созданных после неё.
